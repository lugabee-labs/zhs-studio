## 1. 每集耗时分布与「1.5 倍速」的关系

### 1.1 样本量与总体分布（clean 子集，n = 70）

|---|---|---|---|---|---|---|---|

| 「墙钟/视频」因子 | 1.361 | 1.381 | 1.011 | 1.612 | 0.771 | 1.618 | — |

83 集全量口径下（含未完成集）：视频总长 45,568s（12.66h），实际墙钟 30,748s（8.54h）。

### 1.2 实测倍速：设置 1.5×，实际跑出 1.64×

斜率倍速（n = 70）：

| 指标 | 值 |
|---|---|
| 平均 | 1.631 |
| **中位** | **1.637** |
| P10 / P90 | 1.605 / 1.655 |
| 最短 / 最长 | 1.517 / 1.672 |
| 分档计数 | 1.5× 档 3 集、**1.6× 档 57 集**、1.7× 档 10 集 |

结论与口径说明：

1. **实测进度推进速率是 1.64×，不是 1.5×**，比设置值高约 **+9.1%**。分布极窄（P10 到 P90 只差 0.05），说明这是一个恒定系数，不是随机误差。
2. 产生 +9% 差额的原因，现有数据**无法判定**（可能是平台按分片/取整计入学习时长，也可能是播放器 tick 频率略高于 1Hz）。因此 README 不能写「1.5 倍速跑出 1.5 倍时长」——只能写**实测约 1.64×**。
3. **「墙钟/视频」因子（中位 1.381）不能当倍速用**：它被暂停和重试稀释了。同一批 70 集里，粗口径中位 1.381、斜率口径中位 1.637——若要看"播放有多快"必须用后者。
4. 记录倍速参数的轮次只有 3 个 `meta.json` 带 `params.speed=1.5`（`20261117-173613`、`20261117-173929`，以及被排除的第 15 轮），其余 11 轮是旧 `meta` schema 没有该字段；但**4 个有采样数据的轮次斜率倍速都在 1.63–1.65**，说明实际运行倍速与是否记录无关，一致为 1.64×。

## 2. 风控暂停：`progress.csv` 的停滞段

### 2.1 先纠正一个口径问题

任务里假设的「pct 停滞的**平台**段」，在 14 轮档案里**不存在**。按严格口径（连续 ≥3 个采样、跨度 ≥30s、pct 完全相同）统计：

> **平台侧停滞段 = 0 次 / 85 个有采样的（轮次×集）。**

能观测到的全部「不动」其实是**客户端自己的防检测暂停**，只在采样时间序列里留下空档，事件流里连痕迹都没有：

- `fucker.py`（依赖层）第 545 行：`pause = pause or int(random() < 0.0025) * 60`，即每次循环 0.25% 概率随机暂停 60 秒；
- 暂停期间它仍调用进度回调，但传入的是倒计时 `(60-pause, 60)` 且前缀为 `pause a minute`；
- `app.py` 第 473–474 行对 `prefix` 以 `pause` 开头的回调**直接 return**——既不写 `progress.csv`，也不推 `progress` 事件。

所以：**暂停 = 60 秒倒计时内完全没有采样**，表现为一段 60–70 秒的采样空档；`pct` 在这段时间里"没变"是因为根本没被记录，而不是平台卡住。

### 2.2 统计结果（n = 14 轮 / 2,714 个采样）

| 指标 | 数值 |
|---|---|
| 采样空档（同集 `Δt ≥ 30s`）次数 | **72 次** |
| 时长范围 | 60.4s – 70.6s（全部落在 60–75s 一档） |
| 平均 / 中位 | **65.46s / 65.55s** |
| 合计 | 4,713.1s（1.31h） |
| 涉及（轮次×集） | **42 / 85**（49.4% 的集至少经历 1 次） |
| 每集平均 | 0.85 次 |
| 占 clean 70 集墙钟的比例 | 4,647s / 29,491s = **15.8%** |

### 2.3 按轮次分布

| 轮次 | 状态 | 集数 | 空档次数 | 空档合计 | 平均每次 |
|---|---|---|---|---|---|
| `20261117-173929` | interrupted | 19 | 16 | 1,048.3s | 65.5s |
| `20261118-200544` | captcha | 6 | 8 | 524.9s | 65.6s |
| `20261118-213044` | done | 39 | 38 | 2,486.4s | 65.4s |
| `20261119-112804` | captcha | 9 | 10 | 653.5s | 65.4s |
| 其余 10 轮 | — | 10 | 0 | 0s | — |
| **合计** | | **83** | **72** | **4,713.1s** | **65.5s** |

后 7 轮（`20261118-195745` 起）才有较完整的采样覆盖；早前几轮的采样点只有 0–39 个，天然测不到暂停，因此「0 次」不等于「没暂停」。

### 2.4 与代码假设的一致性校验

72 次 / 29,491s 墙钟 = **0.00244 次/秒**。代码里的触发概率是每次循环 0.0025，反推循环频率 ≈ 0.98 次/秒（≈1 次/秒）。这两个独立数字在 2% 以内吻合，是「空档 = 随机 60 秒暂停」最硬的证据，比任何单一字段都可靠。

### 2.5 给开源项目的直接建议

暂停目前**没有任何显式记录**，只能靠采样空档反推。建议在 `app.py` 的 `_hooked_progress` 里对 `pause` 分支推一条 `kind=pause` 事件（或单独写一列），这样 `events.jsonl` 就能自证暂停，README 才敢写「含 N 次随机暂停」。

## 3. 验证码触发点

### 3.1 检索口径的坑（重要）

按任务给的「`kind=error` 且含 `captcha` 或 `-12`」去检索，**`-12` 命中 0 条**——14 轮档案里根本不存在 `-12` 这个字符串。原因：`fucker.py` 的 `zhidaoQuery` 把 `code == -12` 转成 `CaptchaException("captcha required")` 异常，`app.py` 第 679 行再把它换成中文提示「触发验证码，任务暂停：去浏览器过一下验证再重开」，**错误码本身没有进日志**。

> 因此检索口径必须用 `captcha` / `验证码` / `meta.status == "captcha"`。按 `-12` 检索会得出「从未触发验证码」的错误结论。

### 3.2 按轮次统计

| 轮次 | 触发时刻 | 轮内第几次开播 | 触发时该集已播 | `reason` | 轮次状态 |
|---|---|---|---|---|---|
| `20261118-200544` | 11-18 20:41:41（开跑 35m56s 后） | 第 6 次 | 30.45s | `captcha` | `captcha` |
| `20261119-112804` | 11-19 12:17:45（开跑 9m41s 后） | 第 9 次 | 30.49s | `captcha` | `captcha` |

- 命中率：**2 / 14 轮 = 14.3%**；按开播次数 **2 / 85 = 2.4%**
- 两轮都以 `status=captcha` 收尾，**没有重试**（`app.py` 第 578 行：`CaptchaException` 不重试、直接向上传播）
- 两次都在**开播约 30 秒**时被捕获（30.45s / 30.49s），高度一致

### 3.3 其他风控信号（不是验证码，容易被混为一谈）

| 轮次 | 时间 | 信号 | 出处 |
|---|---|---|---|
| `20261118-200207` | 11-18 20:02:39 | `code: -10 msg: 疑是多窗口观看` | `events.jsonl` 1 条 `error`（随后 `[重试 1/2]`，用户随即手动停止） |
| 未归档轮次（早于第 1 轮） | 11-17 17:09:15 | `code: -8 msg: 学习总时长下降了`（课时 `大学，带给你自我认识的新困境？`） | `data/runs/20261117-170915_67947921.json`（`ok=false`）；此后随 `task-state.json` 被复制进 11 个 `meta.json` 的 `failed` 清单 |

`code -8` 的计数需要特别小心：它**只发生过 1 次**，而且**发生在 14 轮档案之外**（17:09:15 的未归档轮次；`14 轮的 episodes.jsonl` 里没有任何一条记录它）。同集在 17:25:58 的重试里已经成功（`data/runs/20261117-172558_67947921.json`，`ok=true`）。

但因为轮次状态会持久化到 `data/task-state.json` 再带入下一轮，这条失败记录在 **11 个 `meta.json` 里重复出现**。按 `meta.json` 出现次数统计会得到「11 次失败」的错误结论——**正确计数是 1 次，且不属于这 14 轮**。

（另有一条不在 14 轮档案内的历史记录：`data/task-state.json.bak-20261117-162657` 显示 11-17 16:27 前曾有 3 集因代码缺陷 `'dict' object has no attribute 'studyTotalTime'` 失败。这是解析 bug 而非风控，口径外，仅备注。）

## 4. 失败与中断归因

### 4.1 集级 `reason` 分布（样本 83 集）

| `reason` | 集数 | 占比 | 时长特征 |
|---|---|---|---|
| `done` | **72** | 86.7% | 均值 415.6s / 中位 394.6s / 最长 898.9s |
| `stopped` | 6 | 7.2% | 均值 49.3s / 中位 47.6s / 最长 107.2s |
| `captcha` | 2 | 2.4% | 30.45s、30.49s |
| `interrupted` | 0 | 0% | —（不在 `reason` 字段里，见 4.3） |
| `error` | 0 | 0% | —（不在 `reason` 字段里，见 4.3） |
| **无 `reason` 字段（老记录）** | **3** | 3.6% | 均值 157.1s / 中位 88.9s / 最长 326.9s |

### 4.2 无 `reason` 的 3 条老记录（单独归类）

这 3 条来自最早的 2 轮，`episodes.jsonl` **整行没有 `reason` 键**（schema 升级前写入的），不是写了空值。用 `events.jsonl` 逐条核对后，它们的真实性质与「`ok=false` 就是失败」的直觉不同：

| 轮次 | 课时 | `ok` | 墙钟 | 真实判定（依据 `events.jsonl`） |
|---|---|---|---|---|
| `20261117-172736` | 人生没有成败，凡事正面思考 | false | 88.93s | **主动停止**：17:29:05「收到停止请求」→ 17:29:06「已按要求停止」→「收工：成功 0 / 失败 0」 |
| `20261117-172917` | 人生没有成败，凡事正面思考 | true | 55.36s | **断点续播完成**（`pct_start=78.3` → `pct_end=100.0`，只补最后 21.7%） |
| `20261117-172917` | 依恋关系 | false | 326.88s | **主动停止**：17:30:14 开播、答完 2 题，17:35:40「收到停止请求」→「收工：成功 1 / 失败 0」 |

`data/report.md` 把其中两条（`20261117-172736` 的「人生没有成败」、`20261117-172917` 的「依恋关系」）判为「真失败」，是因为它按「无 `reason` + `ok=false`」直接归类，**没有读 `events.jsonl` 的停止记录**。这 3 条全部不是平台侧失败。

处理建议：这类记录只能靠 `ok` 字段 + `events.jsonl` 停止事件 + `meta.failed` 三方交叉判定，**不能按 `reason` 归类，也不能只看 `ok`**。开源版应在 schema 里给 `reason` 补默认值，并保留旧记录的兼容说明。

### 4.3 轮次级状态（`meta.status`，样本 14 轮）

| `status` | 轮数 | 说明 |
|---|---|---|
| `done` | **12** | 正常收工 |
| `captcha` | 2 | 撞验证码（第 3 节） |
| `interrupted` | 2 | `20261117-173613`（0 集）、`20261117-173929`（19 集）。`closed_by = startup-recovery`、`note = 服务进程在任务结束前退出（重启或崩溃），这一轮不是业务失败` |

注意 `interrupted` 与 `done` 可同时成立于同一轮的不同集：`20261117-173929` 状态是 `interrupted`，但 19 集全部 `reason=done`——**中断是轮次级的进程退出，不是集级失败**。统计「成功率」时不能把它算作 19 集失败。

### 4.4 归因小结

- 集级成功 **73 / 83 = 88.0%**；剔除 3 条老 schema 记录后 **73 / 80 = 91.3%**
- 集级未完成 **10 集 = 8 集主动停止 + 2 集验证码**，**平台侧内容失败 0 集**
  （6 条 `reason=stopped`；另 2 条是老 schema 记录，已由 `events.jsonl` 的「收到停止请求/已按要求停止」证实同样是主动停止，见 4.2）
- 交叉验证：10 个写了「收工」事件的轮次里全部是「失败 0」（成功累计 41 集）；其余 19（中断轮）+ 5 + 8（验证码轮）= 32 集没有收工事件，41 + 32 = **73**，与 `ok=true` 计数完全吻合
- 轮级「跑完」**12 / 14 = 85.7%**；2 轮 `interrupted` 是进程退出（`closed_by=startup-recovery`），与业务失败无关
- 平台侧显式拒绝（`code -8`）只有 1 次，且**发生在这 14 轮档案之前**（见 3.3），不影响本档案的成功率

**根因分析：**

1. **不是缺键**：这 7 条的 `q_keys` 与其余 97 条完全一致（8 个键齐全），所以不是 payload 少了字段。
2. **是候选字段的值为空**：`app.py` 第 519–524 行按 `questionContent → name → content → questionName → questionTitle → topicContent → title → question` 顺序取第一个非空值，这 7 条**所有候选字段都是空的**，所以 `stem` 落成 `""`。
3. **推断**（不是直接证据）：从选项内容看（「沙皮狗 / 奥运冠军」「自我认识是一生的任务…」），这批更像图文/情境题，题干在 `imgUrls` 指向的图片里，服务端没有下发文本题干。`q_keys` 里确实有 `imgUrls`，但 `answers.jsonl` **不记录 `imgUrls` 的值**，因此无法进一步证实——要证实需在 hook 里补存 `imgUrls` 或 `questionType`。
4. 时间上集中在最早 2 小时且此后 97 条再未出现空题干，说明是**特定批次题目**的属性，而非解析代码在某轮被改坏。

### 5.5 「作答正确率 100%」是个假指标

104/104 的 `chosen` 与「所有 `correct == true` 的选项集合」完全一致，看起来是完美的 100%。但这不是答题能力：

> `fucker.py` 的 `answerZhidao` 实现是 `[str(opt.id) for opt in q.questionOptions if opt.result == '1']` —— **它直接把服务端下发的正确答案全部提交**。

所以 `chosen == correct` 是**机制决定的恒等关系**，只能用来验证「提交链路没丢项」，**不能作为准确率写进 README**。

其余提交特征：多选提交 2 条（1 条 4 个正确项、1 条 2 个正确项，一次提交全部正确项）；选项数分布 2 项 79 条、3 项 10 条、4 项 14 条、5 项 1 条；正确项数分布 1 项 102 条、2 项 1 条、4 项 1 条。

### 6.2 不能进 README（会被数据打脸或误导）

| 不能写的说法 | 为什么不行 |
|---|---|
| 「1.5 倍速」当作实际性能 | 实测 1.64×（+9.1%），且差额原因未查明 |
| 算术平均倍速 1.36× | 被暂停/重试稀释，与真实播放速率不符 |
| 「平均每集 416.6s」 | 那是**单轮 39 集**（`20261118-213044`）的均值；全量 clean 均值是 421.3s、中位 398.7s |
| 「答题准确率 100%」 | `chosen` 直接取服务端正确答案，是恒等关系，不是能力指标 |
| 「最长单集 899s」当性能 | 该集含重试与暂停，不代表正常耗时 |
| 「12.66h 视频 → 8.54h 刷完」 | 该合计含未完成集、且跨轮次存在重复播放，不能当"总提速" |
| 「平台风控暂停 72 次」 | 72 次是**客户端随机防检测暂停**，平台侧停滞实测为 **0** |
| 「`-12` 错误出现 0 次，所以没触发验证码」 | `-12` 被转成异常+中文提示，**码值不入日志**；实际触发 2 次 |
| 「失败 11 次（按 `meta.json` 计数）」 | `code -8` 只有 **1 次**独立事件，被轮次状态持久化复制进 11 个 `meta.json` |
| 「真失败 2 集」（`data/report.md` 口径） | 那 2 条是「无 `reason` + `ok=false`」的主动停止，`events.jsonl` 明确记录了「收到停止请求」；本档案平台侧失败为 **0** |
| 「14 轮中断 19 集」 | `interrupted` 是**轮次级进程退出**（`closed_by=startup-recovery`），那 19 集 `reason` 全是 `done` |

### 6.3 一句话

> **能进 README 的只有「用采样序列算出来的速率与开销」——实测 1.64×、单集中位 399s、四分之一墙钟耗在每集一次的 60 秒防检测暂停；凡是直接引用 `elapsed` 平均值、`meta` 计数或"100% 正确"的说法，都会在数据面前站不住。**

steps = []                                   # (Δt 秒, Δpct 百分点)
for (t1, p1), (t2, p2) in zip(rows, rows[1:]):

# 1) 斜率倍速：进度斜率(%/s) × 视频时长 = 倍速
